Aethon

An inline Intrusion-Prevention System and TLS-terminating reverse proxy built on Linux eBPF/XDP and AF_XDP kernel bypass, with its own userspace TCP stack.

Aethon runs in front of the web services on a single host. The XDP program steers traffic for the protected ports into userspace through AF_XDP sockets, while all other traffic — SSH, DNS, UDP, IPv6 — is passed straight to the kernel. In userspace, Aethon terminates TCP and TLS itself, inspects the decrypted payload with the Hyperscan regex engine, enforces domain (SNI) and JA3 fingerprint policy, and forwards clean traffic to the backend over loopback.

Problem statement

Inspecting web traffic on one host conventionally requires three or four separate systems — the kernel TCP stack, an IDS such as Suricata (copying every packet to userspace via NFQUEUE), a TLS terminator, and a web-application firewall. This is costly in copies, context switches and memory. Aethon unifies them into a single process on the packet path that drops hostile traffic early, inside the NIC driver, before the kernel allocates any state for it.

02 — System ArchitectureDual-plane design

A kernel data plane and a userspace analytics/control plane

Responsibilities are split between a data plane that runs inside the NIC driver (eBPF/XDP) and a userspace engine connected by zero-copy shared-memory rings (AF_XDP). The data plane makes instant, cheap decisions; the userspace plane does the stateful, expensive work.

Client / Internet → NIC driver (eth0 / veth0)
│ every packet
XDP / eBPF data plane
Protected TCP ports → redirect to AF_XDP · TCP fragments → XDP_DROP · SSH / DNS / UDP / IPv6 → XDP_PASS to the kernel
│ AF_XDP RX ring — zero-copy into UMEM (no syscall, no sk_buff per packet)
Userspace engine — one worker thread pinned per NIC queue
TCP state machine & reassembly → TLS termination (OpenSSL) → Hyperscan DPI → epoll proxy to backend on 127.0.0.1
Each worker owns a private session table; a connection always returns to the same queue via the NIC's RSS hashing, so there are no locks on the hot path.
│ clean flow → backend   |   rule match / policy violation → RST to client
Backend service (nginx / application) · responses returned to the client via the AF_XDP TX ring
03 — Work CompletedWhat is implemented

A functional inline security data path, built from first principles

Data plane · eBPF/XDP

  • Port-based steering of protected services into AF_XDP sockets
  • TCP-fragment dropping (a classic IDS-evasion vector)
  • Multi-queue scaling: one AF_XDP socket and one core-pinned worker per NIC queue
  • Zero-copy bind attempted, automatic copy-mode fallback

Userspace TCP stack

  • Three-way handshake with a SipHash-randomised ISN (RFC 6528)
  • SYN cookies under table pressure (stateless flood defence)
  • Out-of-order reassembly with overlap-evasion detection
  • Bidirectional flow control with real window advertisement
  • RFC 6298 retransmission timer, Reno congestion control, fast retransmit, go-back-N
  • Graceful and half close, FIN retransmission, TCP checksum verification

TLS termination

  • Full termination via OpenSSL memory BIOs
  • Reassembly of a ClientHello split across segments (large modern browser hellos)
  • SNI domain blocklist, including sub-domains
  • JA3 fingerprinting with a per-worker rate limiter

Deep packet inspection

  • Hyperscan in streaming mode — detects patterns split across packets and TLS records
  • Loads thousands of Snort/Suricata rules with a block / alert policy model
  • Direction, unsupported-condition and weak-pattern filtering to avoid false positives
  • Compiled rule database cached to disk: ≈45 s compile → ≈20 ms reload

All of the above is implemented and exercised by the test suite described in Section 04.

04 — Engineering Depth & ValidationHard problems & testing

Non-trivial problems solved, and proven by tests

Representative hard problems

  • TCP overlap-evasion detection (Ptacek & Newsham, 1998): a retransmission that is re-cut at different boundaries must not be mistaken for an attack. Aethon compares only the bytes already buffered (via a bitmap), not the whole range — removing a false-positive that reset legitimate uploads.
  • Two-way flow control & backpressure: the advertised receive window reflects real buffer space, and pressure is propagated both to the client and from the backend, preventing unbounded memory growth.
  • Correct concurrency: a JA3 rate limiter that was shared across worker threads was a genuine data race (the map's internals are not atomic even when the stored values are). It was redesigned as a per-worker limiter — no shared state, no locks — demonstrated with a reproduction of lost updates.
  • Reliable delivery under loss: exact out-of-order byte accounting, retransmission of unacknowledged data, and re-acknowledgement of already-received segments so senders do not stall.

Validation strategy

  • Offline unit & randomized fuzz tests drive the TCP reassembler directly under loss, reordering, duplication, stale replays and corruption — the delivered byte stream must match exactly.
  • DPI coverage test: every blocking rule must detect its own signature; realistic traffic and random uploads must not be blocked.
  • JA3 limiter test, including parallel-worker safety.
  • End-to-end & "torture" suite: real clients (curl, wrk, browsers) traverse Aethon → nginx → a Node.js application under injected packet loss, reordering, slowloris, aborted transfers and spoofed SYN floods.
  • Per-reason event counters report exactly why any connection was reset or dropped.
  • Everything runs from a single command: tests/run_all.sh.
05 — ResultsMeasured, with honest caveats

Correctness demonstrated with real clients

Functional correctness

  • PASS — byte-exact 5–20 MB transfers over both HTTP and HTTPS through the full stack.
  • PASS — the same transfers under injected 50 ms delay and 2% packet loss.
  • PASS — survives slowloris, TLS handshake floods and spoofed SYN floods (SYN cookies hold) while continuing to serve legitimate clients.
  • PASS — deep-packet-inspection blocks malicious payloads even when split across packets or TLS records.
  • PASS — memory remains bounded across heavy connection churn.

06 — Remaining Work & RoadmapToward production

Known limitations and a prioritised path forward

Current limitations

  • IPv4 only — IPv6 is currently passed to the kernel without inspection.
  • No SACK or window scaling — correct, but throughput is limited on long-distance, lossy links.
  • TLS handshakes and logging run on the packet thread — a handshake flood can stall the queue.
  • No global memory budget or fail-open — operational safety features not yet built.
  • Benchmarked on veth, not on a physical NIC.

Roadmap, by priority

  • P0 — fail-open on crash (systemd unit that detaches XDP), a global memory budget, and a monitor-only mode.
  • P1 — real-NIC loss testing, hot-reload of certificates and config, and moving TLS handshakes off the packet thread.
  • P2 — SACK and window scaling, native zero-copy on real hardware, and a full p50/p99/p99.9 benchmark against nginx and Suricata.
  • P3 — asynchronous logging, Prometheus metrics, and fuzzing with sanitizers in CI.

Planned — Central Control Dashboard

A web-based control plane to monitor, configure and control the entire engine from one place, instead of editing files and restarting:

  • Monitor — live throughput, latency, session counts, memory, and the per-reason reset/drop event counters, with alerts.
  • Configure — manage protected services, DPI rule sets, SNI/JA3 policy and rate limits, with hot-reload (no restart, no dropped connections).
  • Control — start/stop and attach/detach XDP, switch monitor-only vs. blocking mode, and block or unblock an IP or fingerprint in one click.
